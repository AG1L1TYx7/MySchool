# Security Audit (14 October 2026)

A full application-security audit of the code at commit `59090b0`, done after the Release 3 review (docs/20) and independently of the per-slice checklist in docs/11 and the attack suite in docs/16: those were treated as claims to verify, not as evidence. Method: the attack surface was split into five slices (secrets and transport; injection, SSRF and files; authentication and authorization; the web client and data exposure; the AI service and integrations), each reviewed read-only against the source with file and line references, plus the dependency audits of both ecosystems and a search of the git history. Findings are listed in section 3, the fixes made in section 4, and what remains for a person in section 5.

## 1. The application and its attack surface

**Shape.** A pnpm monorepo with three deployable parts and one database.

| Part | Technology | Entry points |
|---|---|---|
| `apps/api` | NestJS 11, Prisma 7, MariaDB 10.4 or MySQL 8 | HTTP on port 5000 under `/api/v1` (392 paths, 526 operations in `docs/openapi.json`), Socket.IO for live notifications and messages, scheduled jobs (webhook delivery, retention, usage metering, health checks) |
| `apps/web` | Next.js 15.5, React 19, client components | Port 3000; calls the API through its own `/api` proxy (`next.config` rewrite); the browser never talks to port 5000 directly |
| `apps/ai` | Python 3.12, FastAPI, Ollama (or a fake provider) | Port 8000; called by the API with a bearer service token; calls back into the API's `/internal/ai/*` tool routes with a second token; `/v1/tutor`, `/v1/content`, `/v1/rag`, `/v1/jobs` |
| Database | one schema, 132 models, 26 migrations | reached only by the API |

**Identity.** Eight roles (platform administrator, superintendent, principal, teacher, student, parent, assistant, counselor); local accounts with argon2id passwords, TOTP 2FA, SAML and OIDC single sign-on, LTI 1.3 launches from an outside platform, and API keys for district integrations. Access tokens are JWTs held in browser memory; refresh tokens live in an HttpOnly cookie scoped to the auth path and rotate on use. Every API route declares a feature code and a guard denies by default; organisation (school) and tenant (district) scoping is applied in services.

**Data.** Student education records (FERPA), accommodations and IEP flags, counselor notes, behaviour records, family contact details, AI tutor conversations, uploaded files (outside the web root), H5P packages, portfolio media, invoices and usage. Students under 13 need recorded consent for AI features.

**Inputs from outside the trust boundary.** Sign-in and registration forms; every authenticated API route (validated with a whitelist); file uploads (documents, images, H5P zips, CSV imports); SSO assertions and LTI id_tokens from third-party identity and learning platforms; the payment provider's webhook; URLs supplied by administrators (webhook endpoints, LTI platform endpoints, SSO metadata, library links) that the server later fetches; content authored by teachers and students that other users render (announcements, lessons, messages, community posts, portfolio pages, one public portfolio page per student); and the AI model's output, which is shown to students and teachers.

**Deployment config.** `docker-compose.yml` with one Dockerfile per part; CI in `.github/workflows/ci.yml` (lint, typecheck, unit, e2e on both database engines with a coverage floor and a migration drift check, dependency audits, browser checks); secrets only from the environment with a zod schema that refuses placeholders in production; `.env` files are ignored and have never been committed (checked in the full git history).

**Confirmed before the detailed review.** No `.env` file in any commit; no private key, cloud key or payment key pattern in the history; no `$queryRawUnsafe`/`$executeRawUnsafe` and no string-built SQL (the only raw query is a constant `SELECT 1` health ping; dynamic sort keys go through allow-lists); no `child_process`, `eval` or `new Function` outside the deliberate code sandbox; one `innerHTML` use in the web client, which only empties a container; outbound HTTP from six API modules (AI client, health, LTI, webhooks, push, SSO), each reviewed for SSRF.

### Informational

`/lti/config.json?organizationId=` names any organisation by id; `/metrics` and `/health` are public outside `/api` (not proxied; keep the API port off the internet); the web CSP allows `'unsafe-inline'` scripts (no inline user content today); the MFA token verifier does not pin `algorithms`; `.env.example` ships an `AI_CALLBACK_TOKEN` placeholder too short to pass validation; `frame-ancestors 'none'` contradicts the LTI iframe launch the cookie settings assume; the rate-limit values are read from `process.env` instead of the validated schema; `mariadb:10.4` is past end of life upstream (kept for parity with the XAMPP development database).

## 4. Fixes made

Everything below is in the code, with a unit test for each new pure rule and the affected e2e suites re-run (all 27 suites, in band, against a fresh test database, as CI runs them). Nothing here changes the database schema or how anyone signs in; the four findings that would are in section 5.

## 5. Manual actions and recommendations

### Decisions that change how people sign in or the schema (not made in this audit)

1. **F01 and F02, first-time linking by email.** Today an LTI launch or an SSO sign-in whose email matches an existing account signs in as that account. The safe rule is: never link by email for staff and district roles (an administrator must link the identity from their own settings first, or the roster brings it), and for students and families only with a verified email from a platform or tenant on the district's allowlist, in the same school. Microsoft should be bound to the tenant (`tid`) and object id (`oid`), not the email, with the `common` endpoint removed. Platform registration should be a district-role action. This changes who can sign in through those paths, so it needs your yes.
2. **F16 and F18, two-factor enrolment and lockout.** Enrolling an authenticator should ask for the current password; the MFA token should be single-use; the TOTP step should be claimed with a conditional update so two simultaneous challenges cannot both pass. Lockout should count per account **and** address, answer the same way for a locked and an unknown account, and tell the owner by email. All four alter the sign-in flow.
3. **F11 and F12, LTI nonces and the tool's private key.** Replay protection for launches needs a small `LtiNonce` table (nonce, platform, expiry) and a migration; the tool's signing key should be stored encrypted with `ENCRYPTION_KEY` like TOTP secrets, which is also a migration. Both are schema changes.
4. **F35, minors' public pages.** Whether a student under 18 may publish a public portfolio page without a guardian's or a counselor's approval is a policy choice; the code change is small once chosen (an approval flag on the portfolio, set by a guardian from the family area or by staff).
